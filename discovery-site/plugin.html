One authority core

Two ways to evaluate. One synthetic execution example.

Choose the integration route that fits your local evaluation. Installation alone does not enforce a real external action.

Node.js SDK

Submit the existing v2 business-policy request. Receive a decision and opaque session handle. Changed requests and edited returned decisions cannot create synthetic execution authority.

Local MCP

Start the stdio server with a host-selected absolute state path. Exactly one tool, atg.evaluate_action, is exposed. No execution or administration tool.

Gated synthetic example

Only an enforced ACCEPT can reach the built-in synthetic adapter. Shadow, referral, refusal, expiry and reuse are blocked. Decision and synthetic execution receipts remain separate and linked.

Approval carries signed state

The exact approved business-state snapshot is covered by the GatePass fixture signature. Order or supplier-bank version changes require fresh approval. The destination checks the signed state again at synthetic commit, including a change after preliminary verification.

Uncertainty holds execution

A lost acknowledgement produces UNKNOWN. Destination lookup establishes whether the local order was recorded. The old attempt cannot be retried automatically.

Compare request and outcome

Reconciliation verifies the original signed state binding against the destination record. Invalid recovery evidence retains UNKNOWN exposure. Linked decision, execution and destination records remain inspectable same-host evidence.

Host-controlled evaluation

Keep authority explicit.

  • Use synthetic data; do not provide production credentials or customer data.
  • Keep the absolute state path outside the installed package.
  • Run one process per legacy state file. Optional shared-worker SQLite v2 supports processes on one machine; no multi-machine guarantee.
  • Session handles do not survive restart; lifecycle and exposure records do.
  • No automatic retry after uncertain execution.

Learning and execution verification

Learning remains possible future advisory work: anomaly detection and human-reviewed suggestions. It must not expand authority or rewrite enforcement.

External execution verification, including a possible Salmon connection, is exploratory. No integration or partnership is implemented.

Technical partners and buyer evaluations

Inspect separate worker processes on one machine.

The optional shared-worker SDK and packaged demonstration use local SQLite transactions for approval claims and exposure, with synthetic destination fencing and reconciliation. Legacy SDK, CLI and evaluation-only MCP remain Node 20 compatible.

npx --no-install atg-multi-worker --state C:\ATG-Evaluation\fresh-shared-run-001

Use a new absolute host-owned directory with an existing parent. The command retains SQLite v2 state and results.json; it never removes or reuses existing state. Existing v1 shared directories fail closed: preserve them, do not reset or automatically migrate.

Seven coordinated process scenarios record write counts, reserved exposure and recovery outcomes. Budget observations are inspected before any write. Each scenario supports one synthetic order. New in local.5 · verifier Node 20+ · destination Node 24+

Verify separately signed destination evidence.

A separate synthetic destination process owns its records and generated evaluation signing key. ATG receives only an explicitly pinned public key. Approval and execution evidence stay distinct. Missing, tampered, stale or incomplete evidence retains UNKNOWN exposure; signed absence needs authoritative lookup and completed permanent fencing.

npx --no-install atg-destination-evidence --state C:\ATG-Evaluation\new-destination-run-001
npx --no-install atg-evidence-verify --help

Explicit fresh setup only: parent directory must exist and the run root must be new. Eight cases retain state and public verification inputs. Existing v1/v2 directories are never reset or automatically migrated. Legacy SDK/CLI/MCP and the standalone public verifier support Node 20; destination/shared-worker functionality requires Node 24.

One machine, same-host synthetic destination records, synthetic keys and fixed test clock. Separately signed roles do not establish independent external capture, host-administrator protection, live-time freshness, partner attestation or a live partner integration. No automatic execution retry or reauthorisation.
