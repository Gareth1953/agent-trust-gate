Implemented in the candidate

Approval tied to the exact action.

Human authority

Microsoft Entra support checks the configured tenant, API audience, login application, individual approver, delegated scope and authentication context. The sign-in command uses Microsoft's authentication library and asks the approver to review the exact before-and-after record.

Controlled execution

Separate services persist approval and execution state. One-use admission and conditional record writes reject reused approval and stale record versions. Operator-configured keys and real host time replace built-in demonstration authority on this path.

Inspectable outcomes

The destination signs its persisted outcome. A lost or invalid acknowledgement remains UNKNOWN until authoritative reconciliation. No blind execution retry is provided.

Microsoft Entra setup

Registration completed. Live sign-in still to verify.

ATG's own Microsoft directory and the approval API and approver-client registrations have been created. The delegated approval scope, access-token claims and desktop return address are configured, and administrator consent has been granted.

These are setup milestones, not proof of a completed ATG authentication ceremony. The next step is to configure and verify the required MFA/authentication-strength policy, then exercise an actual Microsoft sign-in through the deployed approval flow.

A buyer can configure its own supported tenant. ATG does not require a commercial partner to set up its own qualification environment.

Tenant policy matters

The configured authentication context must be protected by an enabled Conditional Access policy. An authentication-context claim by itself does not establish MFA. Appropriate Microsoft licensing and tenant administration are required.
