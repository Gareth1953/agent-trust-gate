# Deployment, custody and buyer acceptance gates

The protected threat boundary must be agreed before claiming that the two known
attacks are fixed. This candidate establishes software semantics under a retained
witness assumption; it does not establish that an attacker cannot violate it.

| Actor / asset | Required access in the next deployment | Current observation |
| --- | --- | --- |
| Agent process | Signed grant and bounded execution/lookup channel only | Protocol restriction tested; effective OS denial BLOCKED |
| Approval authority | Independently controlled private signing key and authenticated mandate | Fresh local evaluation key; genuine human mandate NOT VERIFIED |
| Writer | Public authority pin; sole permitted destination-write credential/path | Synthetic SQLite writer only; alternate same-user SQL path remains possible |
| Consumption witness | Atomic one-use/destination state outside agent restore domain | Shared retained SQLite store tested; independent custody NOT PROVEN |
| Controller | Separate authenticated stop/revoke/recovery authority | Trusted host method only; real identity separation NOT PROVEN |
| Host administrator | Explicitly trusted or outside an independently held custody boundary | Common owner can edit/clone all state: security FAIL |

## Mandatory next experiments

1. A named deployment owner provisions the distinct roles and protected runtime,
   configuration, parent directories, keys, DB/WAL/journal, backups and process
   access. Do not infer protection from different directories/processes alone.
2. From the actual agent principal, attempt reads, SQL writes, replacement,
   renaming, debugger/process access, trust-pin substitution and alternative
   destination credentials. Record effective denial and every successful route.
3. Restore all state within that attacker's powers, including copied workflow
   checkpoints and authority envelopes. Keep the independent authoritative store
   outside that restore. Repeated requests must cause at most one protected
   effect. Test unavailability, stale pins and restored stores as explicit holds.
4. If the threat includes the witness administrator or common-host restore,
   supply an independently controlled destination/witness or suitable protected
   monotonic anchor. Adding another local signature or cloning another service
   with the same owner does not remove the counterexample.
5. For an external destination, use its atomic conditional-write/idempotency
   mechanism or a separately designed admission/reconciliation protocol. Do not
   extend this single-database atomicity claim to a payment API. Define UNKNOWN,
   revocation/commit ordering and no-blind-retry behaviour before any live call.
6. Ask an external security assessor to reproduce these cases against the exact
   deployment. Internal tests, framework integration and independent codebases
   are not independent review. No assessor was engaged by this candidate.

## Buyer-defined integration and value test

The included LangGraph graph is a genuine framework integration, with synthetic
approval responses generated by the driver. It is not an autonomous LLM agent,
a buyer-defined workflow or a payment-rail integration. Its reference clock and
human-authority fields are fixtures. No claim of live-time authentication follows.

A prospective buyer should define one protected operation, native baseline
controls, accepted threat model, resource constraints and destination owner.
Compare both configurations fairly on exact approved-action binding, blocked
unauthorised effects, duplicates under failure/retry, audit/reconciliation effort,
latency and resource use. This run does not establish improvements over a
properly configured native framework or a customer's existing controls.

Measure developer installation/configuration time and maintenance effort in a
real buyer exercise; do not infer them from this assistant's setup. Review the
optional Python dependencies and their licences separately. Root MIT terms
and public-code exclusivity limits remain unchanged.

## Cost and permissions

Current work uses an isolated Python environment and synthetic local state.
No paid provider, cloud resource, HSM, real account provisioning, Windows ACL
change, partner credential, payment, external assessor or outreach was used.
The failed sandbox probe was not escalated or bypassed. Before the next deployment,
resolve the exact environment, access and budget; prefer a partner-funded
evaluation where independently held infrastructure can be tested honestly.
