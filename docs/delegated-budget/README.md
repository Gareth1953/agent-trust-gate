# Agent Trust Gate — delegated authority and shared spending (synthetic evaluation)

**12 November 2026. Isolated candidate, production NO-GO.**

## Business question

Can a signed organisation mandate be delegated through two agent identities without widening their permissions, while all agents share one total authorised allowance?

This source experiment adds `src/delegated-budget-witness.ts`, a distinct synthetic writer. It is **not** part of the public plugin, existing OpenShell broker, Entra reviewer companion, a live account, an order system or a production agent-service endpoint.

### Reproducible review

Node.js **24** and the repository's pinned npm dependencies:

```sh
npm ci --ignore-scripts
npm run test:delegated-budget
npm run demo:delegated-budget
```

The buyer demonstration uses an entirely fictional organisation, fixed trusted test time, fresh ephemeral Ed25519 test keys, a temporary SQLite database, two registered agent identities and simulated GBP transactions. There is no external model, card or payment provider.

The seven-step narrative:
1. An attempted action is refused when the supposed authenticated agent identity does not match the leaf of the signed authority chain.
2. Sub-agent B commits a **synthetic** £3,000 operation under a root mandate.
3. Agent A commits another **synthetic** £2,000 operation.
4. A subsequent agent's £1 operation is refused because the combined £5,000 allowance is exhausted.
5. Reuse of an earlier action ID is refused.
6. Historical lookup confirms the already committed synthetic effect; lookup does not authorise a second one.
7. A separately signed attempt to change the permitted supplier in a delegated mandate is refused.

### Control design

- A fixed, trusted root organisation public key signs the starting mandate. The mandate binds an exact domain, tenant, account, supplier, mission, tool, destination, currency, validity window, per-action maximum, maximum total and delegation depth.
- Delegations must be signed by the actual parent key, in order. Each hop may only keep or narrow the supplier, tenant, account, tool, destination, mission, amount, expiry and remaining hop allowance.
- The leaf agent signs the **actual canonical action**, including action ID, amount, resource and chain digest.
- A protected host is expected to supply the agent's authenticated workload identity and pinned credential fingerprint. In this test this input is provided by a fixture, not by actual mTLS or Entra.
- One SQLite transaction checks both the per-mandate limit and the root/account shared ceiling, then records an action and its debit. Different valid mandates cannot reset the root/account limit.
- A simulated `UNKNOWN` reserves exposure. The amount stays held until a separately pinned **Ed25519 outcome-witness key** signs a record bound to the exact action ID and digest. The protected controller verifies that signature before classifying the outcome. A bare agent claim or signed evidence for a different action cannot release exposure.
- Mandate revocation, a stopped writer, stale signatures, expiration, wrong identity, wrong payee/destination and replay are rejected or held as appropriate.
- Tests include two genuine Node.js processes racing separate valid mandates against the same writer database.
- There is no public API for signing mandates, changing registry keys, lifting the ceiling, clearing state or arbitrarily releasing holds.

### Explicit security gaps

**This is not authenticated human approval.** Test keys are generated by a synthetic fixture and there is no verification of real corporate mandate issuance, human understanding or agent mTLS credentials.

**This is not a non-bypassable payment adapter.** The demonstration commits only to the synthetic SQLite effect table; no bank, Shopify order or independent business system is gated.

**Restore resistance remains unproven.** An adversarial test intentionally copies the entire SQLite writer state before use and shows that each copy can commit a nominally single-use action. The successful attack is retained, not relabelled as a pass. The writer and its backup are under the same administrative domain; there is no separate monotonic witness.

**An outcome witness is not independent custody.** The separate outcome-signing key is generated in the same disposable test setup. `reconcileUnknown()` now refuses a bare claimed outcome and requires signed, action-bound evidence from that key. This prevents accidental unsigned clearance in the test but does not prove an external bank event, a separate legal operator or a protected third-party checkpoint. The protected controller and its signer remain trusted.

**No independent assessment, enterprise key lifecycle, cross-host budget, production identity, certified WebAuthn or regulatory claims.** The previous OpenShell and Microsoft Entra demonstrations stay separate.

## Next acceptance gates for buyer scope

1. Select one **buyer-owned** exact destination with genuinely non-bypassable credentials; test direct API/SQL/alternate-route attempts under multiple principals.
2. Bind the agent's identity to a verified enterprise workload credential (e.g. buyer-managed Entra/other issuer), separately from real-person approval and a trusted intent-signing ceremony.
3. Place the one-use checkpoint outside the restorable writer domain; try a coherent cloned writer against the checkpoint and show refusal.
4. Replace the protected test-controller `UNKNOWN` decision with an independently verified destination-outcome query or attestation. Test timeouts, partitions and idempotency expiry.
5. Repeat concurrency and shared-spending checks under the buyer's operational deployment and independent assessment.
6. Keep every historical failure and successful bypass visible. Any failure is a production **HOLD**.

**Decision:** Accept these as new isolated evaluation capabilities only after green targeted, regression and real-OpenShell-preservation checks. Do not represent it as an OpenShell plugin upgrade, Entra integration, real payment control or production-ready agent authority.
